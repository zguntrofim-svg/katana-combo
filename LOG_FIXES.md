# 0.15.1 — разбор присланного журнала

## Исправлено в этом моде

- `Failed to load model .../amakiri_mesh.json` и `kurotsuki_mesh.json`, `Not a JSON Object`. В каталоге `models/` Minecraft обнаруживает все JSON, включая служебную геометрию. Старые файлы были массивами. Теперь это допустимые JSON-объекты с полем `millida_mesh`; собственный загрузчик читает это поле. Координаты, текстуры, масштаб и разворот клинка не изменены.
- `No data fixer registered for katana_combo:raizen`. Vanilla Builder получал ID сущности, для которого нет DFU-схемы Minecraft. Используется `build(null)`, как в FabricEntityTypeBuilder: регистрация с прежним ID в реестре, сохранение и призыв остаются включены, обращения к чужой ванильной DFU-схеме нет. Это сообщение само по себе не доказывало причину зависания.
- Отказ `/millida temple spawn` из-за «существующей структуры». Прежняя проверка `hasStructureReferences` отвергала весь чанк даже при далёкой ссылке либо шахте глубоко под поверхностью. Теперь собираются известные bounding box структур без синхронной подгрузки удалённых start-чанков и проверяется их пересечение с фактическим объёмом размещения. Проверка всех затрагиваемых блоков до начала строительства и повторная проверка перед каждой записью сохранены. Природные руды также разрешены; сундуки и строительные материалы не разрешены.
- Дорогой поиск редкого храма. Ранее один кандидат запрашивал до 81 шумовой высотной колонки, причём до отсеивания неподходящего биома. Сейчас биом проверяется первым, затем центр и четыре точки. Для точного ID `millida:thunder_temple` команда `/locate structure` получает отдельную порционную реализацию: один кандидат за серверный тик, максимум 90 секунд, без join и синхронного перебора тысяч кандидатов в одном тике. Найденный старт подтверждается асинхронной загрузкой одного чанка, чтобы не выдавать несуществующий храм в старых чанках. Прочие структуры и общая команда /locate не изменены. Та же реализация доступна через `/millida temple locate`, отмена — `/millida temple cancel`.

- Проверка прав перенесена на подкоманду `temple`, чтобы регистрация нашего дополнения не ограничивала общий корень `/millida` отдельного клиентского мода Millida.

## Что известно о зависании

В журнале есть тик длительностью более 40 секунд и срабатывание watchdog ModernFix. У серверного потока показаны только верхние кадры `Objects.hashCode` и `DirectMethodHandle`, остальные 87 строк скрыты. Поэтому точный зависший метод по этому тексту установить нельзя. Оптимизация генератора и порционный поиск устраняют обнаруженный в нашем коде источник длительной синхронной работы, но отсутствие повторения зависания без запуска игры не подтверждено. Сторож сервера не отключается, лимит тика не увеличивается, сообщения об ошибках не скрываются.

## Остальные сообщения

- Dynamic FPS рекомендует Mod Menu — это необязательная рекомендация, не ошибка запуска.
- MoreCulling сообщает об отсутствующих refmap; ModernFix и Lithium — о пропущенных конфликтующих оптимизациях. Это сообщения сторонних модов; их исходников в проекте нет.
- Sodium применил защитный обход для AMD. Он сообщает о включённом workaround, а не о падении нашего мода.
- Отсутствующие звуки козы и `Sampler2` у стандартного shader — сообщения клиентских ресурсов/рендеринга. Собственных shader JSON или этих sound events в моде нет.
- OpenAL `Stop: Invalid name parameter` не сопровождается стеком вызова, позволяющим установить источник. Собственные звуки защиты используют зарегистрированные ванильные trident/shield events; без полного звукового стека исправлять чужой звуковой движок оснований нет.

Игра и автоматические тесты по просьбе пользователя не запускались. Выполнена только сборка устанавливаемого JAR. Для самостоятельной проверки: заменить предыдущий JAR на клиенте и сервере, выполнить отдельно `/millida temple spawn` либо `/millida temple locate`, дождаться сообщения. В чат нужно вводить саму команду, без маркеров списка и поясняющего текста.
